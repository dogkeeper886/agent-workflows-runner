# #1

**Key point.** Every write travels three refusals in a fixed order — Fastify JSON Schema, then the bound Rules, then the `testlink-mcp` call — and nothing reaches TestLink until all three clear; reads travel none of them and are never refused, they carry what fired beside the content they serve. The three refusals answer in three distinguishable shapes (`400 {refusal:'schema'}`, `422 {violations}`, `404 {message}`), so a caller never has to read a string to know which stage stopped it.

**Ground truth.**
- `/home/jack/src/testcase-validator/src/app.ts` (whole file; schemas lines 26–126, `reject` 179–185, `setErrorHandler` 188–193, `nothingThere` 201–202, routes 204–431)
- `/home/jack/src/testcase-validator/src/violation.ts`
- `/home/jack/src/testcase-validator/src/testlink-client.ts` (the `TestLinkClient` interface, lines 91–125)
- `/home/jack/src/testcase-validator/src/server.ts` (lines 79–88, composition)

**Mechanism.** `buildApp({testlink, documents, rules, logger})` builds Fastify with `ajv.customOptions.coerceTypes: false`. `testCaseSchema` (`required: ['name','summary']`, `additionalProperties: false`) is attached as `schema.body` on `POST /projects/:projectId/suites/:suiteId/test-cases` and `PUT /test-cases/:id`. A schema failure reaches `setErrorHandler`, which sees `error.validation` and answers `400 {refusal:'schema', message}` — carrying no `violations` key, so it cannot be misread as a Rejection. Otherwise `findViolations(request.body, bound.testCase)` runs; a non-empty array goes to `reject()`, which emits one `request.log.warn({ruleSetVersion, field, rule}, 'Rule violated')` per Violation and answers `422 versioned({violations})`. Only then is `testlink.createTestCase` / `updateTestCase` called. `undefined`/`false` back from the client becomes `nothingThere(reply, ...)` → `404 {message: 'TestLink holds no ...'}`. Success is `201 versioned(written)` or `200 versioned({id})`. Reads (`GET /test-cases/:id`, `GET /reference-documents/:id`) call `findViolations` too but always send `200` with `{testCase|document, violations}` — the Violations sit beside the content, never merged into it. `GET/POST/PUT/DELETE` on `/projects` and `/projects/:projectId/suites/...` run schema only: no Rule binds to a Project or a Suite.

**Why it matters.** This ordering is the product. If the Rules stage could be reached after the write, or if a Rejection could be confused with a schema refusal or with absence, the whole trust-boundary argument collapses — the agent would have a way to get unchecked prose into TestLink, or a way to read "not there" as "rejected" and stop trying.

**Diagram.**

```

     │
     ▼  POST /projects/:projectId/suites/:suiteId/test-cases
 ┌─────────────────────────────────────────────────────────┐
 │ (1) Fastify ajv, testCaseSchema, coerceTypes:false      │
 │     fail ──► setErrorHandler ──► 400 {refusal:'schema'} │──┐
 ├─────────────────────────────────────────────────────────┤  │
 │ (2) findViolations(body, bound.testCase)                │  │ nothing
 │     len>0 ──► reject(): log.warn ×n ──► 422 {violations}│──┤ written
 ├─────────────────────────────────────────────────────────┤  │

 │                                   ── {id}      ──► 201  │──► TestLink

```

**Contradicts.** Nothing in #1 contradicts the docs. README lines 3–6, 220–231 and 344–346 describe exactly this ordering and these two response shapes.

**Paths.**

- **1a.** POST a Test Case body carrying an extra key (`{"name","summary","title"}`) → `additionalProperties:false` → `400 {refusal:'schema'}` and **no** `violations` key → **the named Test Suite in TestLink holds no Test Case by that name** (query TestLink for the suite's cases). *NOT fake-assertable* — a stub can only report that `createTestCase` was not called.

- **1d.** POST with `summary: 5` (number) → coercion is off → `400` → **nothing in TestLink, and no case with summary "5"**. *NOT fake-assertable.*
- **1e.** PUT `/test-cases/:id` over an existing case with a violating body → `422` → **the Test Case in TestLink still holds its previous `name` and `summary` verbatim**. *NOT fake-assertable* — this is the one that proves a Rejection is not a partial write.
- **1f.** PUT the same violating body twice → two byte-identical `422` bodies → **TestLink unchanged after both**. *NOT fake-assertable* (the identical-body half alone is fake-assertable).
- **1g.** GET `/test-cases/:id` for a case stored in TestLink that violates several Rules → `200`, content served unchanged, `violations` beside it → **the TestLink record is byte-identical after the read** (a read must not rewrite). *NOT fake-assertable.*
- **1h.** POST `/projects/:projectId/suites` with `{"name":"S","parentSuiteId":"X"}` → schema passes, no Rule runs → `201` → **TestLink shows the new Suite nested under suite X, not at project root**. *NOT fake-assertable.*
- **1i.** PUT `/projects/:projectId` with `{}` → `minProperties:1` → `400 {refusal:'schema'}` → **the Project's settings in TestLink are unchanged**. *NOT fake-assertable.*
- **1j.** A violating POST produces exactly one `log.warn` line per Violation, each carrying `ruleSetVersion`, `field`, `rule`. *Fake-assertable.*

# #2

**Key point.** Startup is the gate, and after it the database is a read-only input that no request can change. The server reads its Rules from `rules`/`rule_exceptions` **once**, refuses to start on a missing setting, on an empty result, or on any row it cannot bind — and afterwards nothing in the process can write a Rule or a Reference Document, so the `Rule-Set-Version` derived from those rows is fixed for the life of the process and rides on every single answer.

**Mechanism.** `server.ts` top-level `await`s: `connectToPostgres(required('DATABASE_URL'))` → `new PostgresStore(...)` → `await store.rules()`. `rules()` first asks `select 1 from information_schema.tables where table_name='rules'` (`hasSchema`) so an un-applied schema answers `[]` rather than throwing; then `select ... from rules where enabled order by id` plus a separate `select rule, phrase from rule_exceptions where enabled order by id` folded into a `Map<number,string[]>` keyed by `rules.id`. Zero rows → the explicit `throw new Error('No enabled Rules are in the database, so the server will not start. Apply schema.sql and insert a Rule ...')`. Inside `buildApp`, `bindRules(rules)` runs `checkStoredRule` over every row and `refuse()`s with *all* problems joined, before Fastify exists. `ruleSetVersionOf(rules)` is a sha256, sliced to 12 hex chars, over `JSON.stringify([contentKind, field, ruleId, category, looksFor, flanked, reason, sortedExceptions])` per row, `.sort()`ed then newline-joined — so row `id` and database ordering are excluded, and disabled rows never reach it. An `onSend` hook stamps `Rule-Set-Version` on *every* reply including the `204`s; `versioned()` puts `ruleSetVersion` in the body only where Rules took part. The whole write direction is absent by construction: `PostgresStore` has `rules`, `listDocuments`, `getDocument` and nothing else, and `DocumentStore` declares only the two reads. `schema.sql` and `default-rules.sql` are operator-applied (`psql -f`), never referenced from `src/`.

**Why it matters.** Two guarantees stand on this and nothing else: a running server cannot be talked into loosening a Rule (there is no object in the process that can write one), and a Violation reported today can still be explained tomorrow (the version names the exact Rules that judged it). Both are unfalsifiable without a real database — the write-absence claim is a claim about rows, not about method calls.

# #3

**Key point.** One `testlink-mcp` tool call is read into four outcomes — content, *absent*, *unconfirmed*, or an outage — and the HTTP status code is decided entirely there. Absence is inferred only from what TestLink said **about the call** (`does not exist` / `not found` in an error or in a code-and-message where a result belongs), never from served content; a version mismatch (`Unknown tool`) throws naming `1.6.0`; a `status:false` reply or a create that reports no id throws even though the call "succeeded"; and everything unrecognised escalates as an outage rather than being answered as "not there".

- `/home/jack/src/testcase-validator/src/server.ts` lines 40–77 (the pinned `docker run ... testlink-mcp:1.6.0`)
- `/home/jack/src/testcase-validator/.mcp.json.example`, `/home/jack/src/testcase-validator/docker-compose.yml` (the `dogkeeper886/testlink-code` fork, pinned `mcp-1.0.0`)

**Mechanism.** `connectToTestLinkMcp` spawns the MCP server over `StdioClientTransport` and flattens its reply to `{text, isError}` — the only structural signal there is. `McpTestLinkClient.answer(tool, args, alsoTheCallers?)` calls it, then: `isError` → `place(tool, text, alsoTheCallers)`; otherwise `JSON.parse(result.text)` and `reportedProblem(content)` (first element carrying both a `code` and a string `message`) → `place(...)`; then `deniedIn(content)` (`status === false`) → `throw 'TestLink did not complete <tool>: ...'`; otherwise the content. `place` tries, in order: `alsoTheCallers` → `unconfirmed`; `reportsMissingTool` (`/Unknown tool/i`) → `throw 'testlink-mcp does not provide <tool>, so it is older than the 1.6.0 this client calls'`; `reportsAbsence` (`/does not exist|not found/i`) → `absent`; else `throw 'TestLink could not be reached through <tool>: ...'`. `deleteProject` is the only call passing `alsoTheCallers = reportsUnconfirmed` (`/Confirmation failed/i`) and answers the three-valued `ProjectDeletion`. `idOf` reads `first(content).id ?? first(content).additionalInfo.id` and throws when it is missing, `''` or `0` — "answering an id here is what makes the write complete". `listProjects` and `createProject` treat `absent` as nonsense and throw. A stub that is written to emit those strings proves that the regex matches the stub — nothing more.

# #4

**Key point.** What actually fires is decided by four interacting semantics, per Field, independently, all in one pass: a **Term** matches its words in any casing and however they are spaced (whitespace collapses to `\s+`) but only where it stands as a word, with a hyphen and an underscore counting as *inside* a word; a **Symbol** is one code point matched anywhere, unless `flanked='whitespace'`, where the edge of the Field counts as whitespace; and an **Exception** suppresses a firing only where the match falls **wholly inside** a span the Exception covers, and only for the one Rule it hangs off.

**Ground truth.**
- `/home/jack/src/testcase-validator/src/violation.ts` (`findViolations` 28–56, `suppressedSpans` 71–73, `isSuppressed` 81–85, `termViolations` 88–104, `matcherFor` 123–127, `standsAsWord` 134–136, `isOutsideAWord` 143–145, `symbolViolations` 148–165, `flankedByWhitespace` 172–174, `isGap` 177–179)
- `/home/jack/src/testcase-validator/src/rule-set.ts` (`TermRule`/`SymbolRule`/`RuleIdentity` 67–92, `checkStoredRule` 125–179)
- `/home/jack/src/testcase-validator/schema.sql` (`a_symbol_is_one_character`, `only_a_symbol_is_flanked`, `field_belongs_to_the_content`)
- `/home/jack/src/testcase-validator/default-rules.sql` (74 Terms lines 53–139, 15 Symbols lines 154–185, the five-Field cross join, the honesty note at 195–217)

**Mechanism.** `findViolations(content, ruleSets)` walks `Map<Field, RuleSet>`, skips a Field the content does not carry (`preconditions` optional), and for each Rule computes `fired` then `suppressed = suppressedSpans(value, rule.exceptions)` — that Rule's Exceptions alone — and filters. `matcherFor` escapes regex metacharacters then replaces `\s+` runs with `\\s+`, flags `giu`. `termViolations` keeps only spans where `standsAsWord`, which tests the characters either side against `/[\p{L}\p{N}_-]/u`, `undefined` (Field edge) counting as outside. The reported `text` is the casing **found**, with `offset` its start. `symbolViolations` uses `indexOf` in a loop, applying `flankedByWhitespace` when `rule.flanked === 'whitespace'`, with `isGap(undefined) === true`. `isSuppressed` requires `offset >= span.start && offset + text.length <= span.end`. "One character" is enforced twice with the same reading: `looks_for like '_'` in Postgres, and `[...looksFor].length !== 1` in `checkStoredRule` — both count code points, so an em dash passes and a glyph carrying a variation selector does not. `default-rules.sql` cross-joins 89 checks against five Fields, producing 445 independent Rules; there is no inheritance and no cross-field Rule.

**Why it matters.** This is what a caller experiences as "the validator". Every one of these boundaries has a plausible wrong answer that would look identical in a green suite — `utilises` flagged, `re-associates` flagged, a phrase silently defeated by a line break, an Exception written for one Rule quietly suppressing another. And 445 Rules on five Fields means the wrong answer arrives 445 times.
